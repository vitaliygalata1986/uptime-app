# Работа с миграциями PostgreSQL

Гайд для агента, который меняет схему или переносит данные в этом проекте. Следуйте [общим правилам](../../AGENTS.md) и [правилам backend](../../backend/AGENTS.md). Начните отдельную задачу по [GitHub Flow](../rules/github-flow.md); продолжение текущей задачи остаётся в её ветке и PR.

## Где всё лежит и как работает

| Путь от корня репозитория | Назначение |
| --- | --- |
| `backend/internal/store/migrations/*.sql` | Версионированные SQL-файлы Goose с секциями `Up` и `Down` |
| `backend/internal/store/store.go` | `//go:embed migrations/*.sql`, подключение GORM и `Store.Migrate`: `goose.NewProvider` → `provider.Up` |
| `backend/cmd/api/main.go` | Открывает БД, вызывает `Migrate`, затем запускает HTTP |
| `backend/internal/store/` | Модели GORM, запросы и транзакции, которые должны соответствовать схеме |
| `backend/internal/httpapi/*integration_test.go` | Интеграционные проверки миграций и HTTP с настоящей PostgreSQL |
| `backend/go.mod`, `backend/Dockerfile` | Версия Goose и сборка бинарника с SQL-файлами внутри |
| `compose.yaml` | БД приложения и API; постоянные volumes `postgres_data` и `avatar_data` |
| `compose.test.yaml` | Отдельная тестовая PostgreSQL в `tmpfs`, сборка, vet и race-тесты |
| `backend/README.md` | Подготовка `.env`, запуск, API и HTTP smoke-проверка |

На момент создания гайда есть версии `00001_auth.sql`, `00002_user_name.sql`, `00003_user_avatar.sql`, `00004_monitors.sql`. Перед новой задачей проверьте фактический список: номер следующей миграции нельзя брать только из этого документа.

Миграции запускаются автоматически при каждом старте API, до сообщения `API listening`. При ошибке процесс завершается с `migrate database: ...`; HTTP не запускается. Подключение к БД и миграции используют общий стартовый контекст на 30 секунд. Длительный backfill нужно планировать отдельно, а не помещать целиком в запуск API.

Goose хранит историю в таблице `goose_db_version`. Повторный `Migrate` пропускает уже применённые версии. Он не исправляет SQL в старом файле после его редактирования. GORM использует ту же БД; `AutoMigrate` в проекте не применяется.

SQL встроен в бинарник. После добавления файла нужна **пересборка** API: `restart` существующего контейнера не включит новую миграцию. В runtime-образе нет отдельной команды приложения для `status`, `up` или `down` и не установлен Goose CLI.

## 1. Подготовить изменение

Все команды ниже выполняются из `backend/`, кроме явно отмеченных команд из корня репозитория.

1. Прочитайте существующие SQL-файлы, затронутые модели, запросы, DTO и интеграционные тесты. Определите, какие данные уже есть и как они должны выглядеть после обновления.
2. Запишите ожидаемую схему: типы, `NULL`/`NOT NULL`, значения по умолчанию, ограничения, внешние ключи и индексы. Отдельно опишите преобразование существующих строк.
3. Добавляйте изменения новыми файлами. Не переименовывайте, не перенумеровывайте и не редактируйте уже применённые миграции; ошибку выпущенной миграции исправляйте следующей версией.
4. Предпочитайте совместимые добавления. Для обязательного поля предусмотрите корректное значение старым строкам; если это невозможно одним безопасным шагом, разделите добавление поля, заполнение данных и усиление ограничений. Удаление или переименование используемого поля требует согласованного обновления потребителей и отдельного плана сохранения данных.
5. До применения к БД с нужными данными определите резервную копию, способ восстановления и допустимое время блокировок. Тесты всегда направляйте в отдельную тестовую БД.

Проверить занятые версии и публикуемый порт:

```sh
rg --files internal/store/migrations | sort
rg '^API_PORT=' .env
```

Реальный `.env` подготовьте по [backend/README.md](../../backend/README.md). Не выводите его целиком и не включайте секреты, дампы или токены в коммит и отчёт. Бинарник сам `.env` не читает — файл обрабатывает Compose.

## 2. Создать SQL-файл по шаблону

Имя: `<следующая_версия_из_пяти_цифр>_<описание_snake_case>.sql`. При текущих четырёх файлах следующая версия — `00005`; после обновления ветки проверьте отсутствие конфликта номера.

Ниже пример для гипотетического поля `timezone`, **не требование добавить его в проект**. Замените имя и SQL под задачу:

```sql
-- +goose Up
ALTER TABLE users ADD COLUMN timezone TEXT NOT NULL DEFAULT 'UTC';

-- +goose Down
ALTER TABLE users DROP COLUMN timezone;
```

Секция `Up` содержит прямое изменение, `Down` — обратное в порядке, учитывающем зависимости. Удаление столбца в этом примере теряет его данные: наличие `Down` не означает возможность восстановить значения. Не используйте `IF NOT EXISTS`, чтобы скрыть расхождение ожидаемой и реальной схемы.

Сохраняйте транзакционный формат существующих миграций. Операции вроде `CREATE INDEX CONCURRENTLY`, требующие выполнения вне транзакции, нуждаются в отдельном плане применения и восстановления после частичного сбоя. Не добавляйте `NO TRANSACTION` механически. Для сложного SQL с внутренними `;`, например функций, используйте Goose-маркеры `StatementBegin` / `StatementEnd` вокруг целого выражения.

Если поле используется приложением, синхронно обновите модель и запросы в `internal/store/`, затронутые сервисы, DTO и HTTP-проверки. Публичный ответ не должен автоматически раскрывать всю GORM-модель.

## 3. Проверить на изолированной PostgreSQL

Из `backend/`:

```sh
docker compose -p uptime-auth-tests -f ../compose.test.yaml up \
  --build --abort-on-container-exit --exit-code-from tests
# Сначала сохраните результат проверки и нужные логи, затем удалите тестовые контейнеры:
docker compose -p uptime-auth-tests -f ../compose.test.yaml down
```

Ожидается код завершения `0` первой команды и успешные сборка, `go vet ./...`, `go test -race -count=1 -v ./...`. Команда `down` не заменяет результат тестов. Этот Compose-проект использует отдельную БД с `tmpfs`; её содержимое временное. Не подставляйте конфигурацию БД приложения в `TEST_DATABASE_URL`.

При локальном Go 1.27+ альтернативные команды:

```sh
go build -o bin/api ./cmd/api
go vet ./...
# TEST_DATABASE_URL должен быть заранее задан для отдельной тестовой PostgreSQL.
go test -race -count=1 -v ./...
```

Без `TEST_DATABASE_URL` интеграционные тесты пропускаются. Успех unit-тестов в таком запуске не подтверждает работу миграции. Тестовый пользователь должен иметь право `CREATE SCHEMA`: helper `integration` создаёт случайную схему, задаёт `search_path`, дважды вызывает `Migrate` и удаляет схему при завершении.

Для новой миграции проверьте следующие сценарии и добавьте недостающие интеграционные проверки:

- **Пустая БД:** весь набор миграций применяется последовательно; новые таблицы, поля, ограничения и индексы соответствуют задаче.
- **Обновление существующей БД:** в схеме предыдущей версии создаются старые записи, затем применяется новая миграция. Сравните ID, связи, прежние значения и ожидаемое заполнение новых полей; проверьте работу изменённых запросов/API.
- **Повторный запуск:** второй `Migrate` успешен, не дублирует преобразованные данные и записи применённой версии.
- **Ограничения:** некорректные строки отклоняются, допустимые сохраняются; проверяйте именно новые ограничения и связи.
- **Обратный переход:** если план восстановления использует `Down`, отдельно выполните его на одноразовой копии БД и проверьте последующее `Up`. Штатный набор тестов автоматически `Down` не вызывает.

Ориентиры: `TestIntegrationRegistrationAndMigrations`, `TestIntegrationProfileMigrationPreservesUsers`, `TestIntegrationAvatarMigrationPreservesUsers`, `TestIntegrationMonitors` в `internal/httpapi/`. Profile/avatar-тесты вручную воссоздают старую схему и удаляют строки истории **только в случайной тестовой схеме**. Новые зависимости могут потребовать обновления этой подготовки. Не переносите такой способ «отката» в БД приложения. Текущие тесты не заменяют проверку перехода предыдущая версия → ваша новая версия.

## 4. Применить в целевом окружении

После успешной изолированной проверки убедитесь, что выбраны нужные окружение, Compose-проект, `.env` и volume. Команды ниже относятся к локальному стеку репозитория; для другого окружения используйте его проверенную процедуру резервного копирования и выпуска.

Перед изменением БД с нужными данными сохраните резервную копию и проверьте её восстановление в отдельную БД. Пример создания дампа локальной БД без вывода пароля:

```sh
MIGRATION_BACKUP_DIR=$(mktemp -d /tmp/uptime-migration-backup-XXXXXX)
docker compose -f ../compose.yaml --env-file .env exec -T db \
  sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' \
  > "$MIGRATION_BACKUP_DIR/database.dump"
```

Проверьте код завершения `pg_dump`; наличие файла само по себе не подтверждает успешную копию. `/tmp` — временное место: перенесите проверенный дамп в предусмотренное хранилище резервных копий. Для восстановления всего приложения также нужен volume `avatar_data` с файлами; дамп БД его не содержит.

Зафиксируйте исходную историю миграций и контрольные записи, затем пересоберите и запустите API:

```sh
docker compose -f ../compose.yaml --env-file .env up --build -d api
docker compose -f ../compose.yaml --env-file .env ps
docker compose -f ../compose.yaml --env-file .env logs --tail=100 api
```

`up -d` сообщает о запуске контейнера, а не об успехе миграции. В логах не должно быть `migrate database: ...`; ожидается `API listening`. При длинной миграции учитывайте общий стартовый лимит 30 секунд; повторные рестарты не заменяют диагностику.

Не используйте `down -v` для обновления: он удаляет volumes с БД и файлами. Обычные пересборка API и `restart api` сохраняют данные. Порт БД на хост не опубликован; SQL выполняйте через контейнер `db`.

## 5. Проверить результат в БД и через API

Следующую команду можно выполнить до и после обновления; до первого запуска на пустой БД таблицы истории ещё нет:

```sh
docker compose -f ../compose.yaml --env-file .env exec -T db \
  sh -c 'psql -X -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' <<'SQL'
SELECT current_database(), current_schema();
SELECT version_id, is_applied FROM goose_db_version ORDER BY id;
SQL
```

Сопоставьте историю с файлами: новая версия должна иметь запись `is_applied = true`, повторный запуск не должен добавлять её снова. Служебная версия `0` допустима. Одной максимальной версии недостаточно — проверьте ожидаемые предыдущие версии и реальную схему.

Через ту же команду `psql` выполните SQL под конкретную задачу: проверьте столбцы и default/nullable через `information_schema.columns`, ограничения через `pg_constraint`, индексы через `pg_indexes`, значения контрольных строк до и после миграции. Укажите таблицы, ожидаемые значения и фактический результат в отчёте; не публикуйте персональные данные и хеши учётных данных.

Адрес возьмите из фактического `API_PORT` в `.env`. Ниже пример для порта `8081`; при другом значении измените `API_URL`:

```sh
API_URL=http://localhost:8081
curl --fail-with-body -sS "$API_URL/healthz"
python3 scripts/http_smoke.py --url "$API_URL"
```

Дождитесь HTTP `200` от `/healthz`. Этот маршрут подтверждает готовность HTTP и БД; он не проверяет состав схемы или сохранность всех данных. `http_smoke.py` проверяет авторизацию и создаёт тестовые аккаунты; запускайте его в локальном/проверочном окружении. Для другой среды выберите согласованный сценарий проверки.

Отдельно проверьте изменённую функцию: HTTP-ответ → запись в БД → повторное чтение. После успешного старта перезапустите API и повторите проверку истории и контрольных данных:

```sh
docker compose -f ../compose.yaml --env-file .env restart api
```

Снова дождитесь `/healthz` и прочитайте данные через API. Для проверки сохранения пользователя и refresh-сессии при пересоздании контейнеров используйте фазы `prepare` / `verify` из раздела «Миграции и проверки» в [backend/README.md](../../backend/README.md).

## Если миграция завершилась ошибкой

Сохраните ошибку, версию бинарника, историю Goose и фактическую схему. Проверьте выбранную БД, права, ограничения старых данных, блокировки и стартовый таймаут. Успешные более ранние миграции могли уже сохраниться, даже если следующая не выполнилась. После нетранзакционных операций возможен частичный результат — сначала исследуйте состояние.

Не удаляйте строки `goose_db_version`, не помечайте версию применённой вручную и не пересоздавайте volume ради успешного запуска. Для уже выпущенного изменения подготовьте исправляющую миграцию; для ещё не применённого файла в текущей задаче исправьте SQL и повторите изолированную проверку.

Автоматического `Down` при ошибке или откате образа нет. Старый бинарник сам не отменит изменения БД. Если нужен обратный переход, подготовьте отдельную процедуру для конкретной версии с совместимым инструментом Goose, закреплённым по `backend/go.mod`, и сначала проверьте её на копии. Для необратимых изменений используйте проверенную резервную копию с учётом записей, появившихся после её создания. Выполнение SQL из `Down` вручную без согласования истории Goose не является корректным откатом.

## Шаблон отчёта о выполнении

```text
Миграция: <файл, версия, назначение>
Окружение: <локальное / тестовое / другое, без секретов>
Переход: <исходная версия> → <целевая версия>
Данные: <что сохраняется, как заполнены новые поля>
Восстановление: <проверенная копия / процедура, ограничения Down>
Статические проверки: <сборка, vet, git diff --check; результаты>
Интеграционные проверки: <пустая БД, обновление, повторный запуск; результаты>
Runtime: <история Goose, схема, HTTP, чтение после рестарта; результаты>
Пропущено: <какие проверки не выполнены и почему>
```

Из корня репозитория выполните `git diff --check` и просмотрите итоговый diff. В PR включите новую SQL-миграцию, связанные изменения кода и тестов; явно отделите статические проверки от интеграционных и runtime-проверок. Создание файла, сборка или один успешный `/healthz` сами по себе не доказывают корректность переноса данных.
