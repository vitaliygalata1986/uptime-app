# Проверка Axios после замечания в PR #1

Проверено 2026-11-13. Сценарий: формы авторизации, точек мониторинга и профиля → общий транспорт Axios → Go API → отдельная PostgreSQL → обновлённый интерфейс. Замечание: [перейти с fetch на Axios instance с авторизацией](https://github.com/vitaliygalata1986/uptime-app/pull/1#issuecomment-6856010718).

## Реализация

`frontend/src/lib/api.ts` создаёт Axios clients с адресом API, credentials и таймаутом 15 секунд; ошибки приводятся к существующему `ApiError`. Публичные auth-запросы используют client без access-токена. В `session.ts` отдельный защищённый instance добавляет актуальный токен из памяти синхронным request interceptor непосредственно перед отправкой. Токен не записывается в Axios defaults или web storage. Существующий механизм авторизации сохраняет single-flight refresh, Web Locks и не более одного повтора после 401, а также проверку поколения сессии перед запросом и после ответа.

Вызовы авторизации, профиля, создания точек и загрузки файлов используют `data`: JSON-объект либо `FormData`. Axios формирует JSON Content-Type и multipart boundary.

## Автоматические проверки

Из `frontend/` на Node.js 24.6.0:

```sh
npm test
npm run lint
NEXT_TELEMETRY_DISABLED=1 npm run build
NEXT_PUBLIC_API_URL=http://localhost:18081 NEXT_TELEMETRY_DISABLED=1 npm run build
```

Прошли ESLint, production-сборка и TypeScript. Семь тестов встроенного Node.js test runner исполняют реальные transport/auth-модули и Axios interceptors с управляемым адаптером:

- Успешный ответ после выхода и ответ повтора после 401 не возвращают данные старой сессии.
- Вход в другой вкладке сразу скрывает прежний аккаунт.
- JSON и multipart защищённых запросов получают Bearer-токен централизованно; refresh/logout не получают его.
- Два одновременных 401 используют общий refresh; повторные запросы отправляются с актуальным токеном. Постоянный 401 не вызывает бесконечных повторов.
- Сохраняются коды ошибок API, обработка сетевой ошибки/таймаута, некорректного JSON и пустого ответа 204.

Из корня `git diff --check` проходит. Backend-код в этом исправлении не менялся; его build/vet/race/integration-проверки успешно выполнены 2026-11-13 при подготовке PR.

## Chrome, API и PostgreSQL

Использованы production frontend на `localhost:3100`, временный API на `localhost:18081` и отдельная PostgreSQL проекта `uptime-axios-review`. Конфигурация, Playwright и сценарии находятся только в `/tmp/uptime-axios-review.yaml` и `/tmp/uptime-pr-browser/`. Рабочие данные приложения не использовались.

Подтверждены реальные регистрация, вход, выход, создание точки, PATCH имени и multipart-загрузка PNG-аватара вместе с именем. В продолжении браузерного сценария проверены XHR-запросы Axios, автоматический Authorization на защищённых маршрутах и отсутствие access-токена на публичных auth-маршрутах.

Для проверки повтора один POST `/api/monitors` получил подставленный 401: браузер выполнил ровно один дополнительный реальный refresh, HttpOnly-cookie с Path `/api/auth` изменилась, повтор POST вернул созданную точку. Один ответ создания был подменён на `409 monitor_limit`: форма показала сообщение о квоте, сохранила URL, повтор создал точку через реальный API.

После перезагрузки и повторного входа точки остаются в списке. SQL-запрос в тестовой PostgreSQL подтвердил три записи того же владельца с интервалом 600 секунд, имя `Axios Avatar User` и непустой `avatar_url`. LocalStorage/sessionStorage пусты, необработанных JavaScript-ошибок в завершающем сценарии нет.

Переключение аккаунтов между вкладками и задержанные ответы проверены автоматическими регрессионными тестами; расширенная браузерная проверка этих гонок остаётся в [отчёте от 2026-11-11](monitor-security-verification.md). Общая загрузка произвольных файлов проверена управляемым Axios-адаптером; в браузере multipart проверен через загрузку аватара.
