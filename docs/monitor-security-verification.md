# Проверка исправлений после ревью мониторов

Проверено 2026-11-11. Изменения: изоляция состояния между аккаунтами, квота и ограничение частоты, пагинация, регистрация HTTP-методов и разделение формы/загрузки списка.

## Автоматические проверки

Из `backend/`:

```sh
docker compose -p uptime-auth-tests -f ../compose.test.yaml up --build --abort-on-container-exit --exit-code-from tests
```

Прошли `go build`, `go vet`, `go test -race -count=1 -v ./...` с отдельной PostgreSQL. Новые интеграционные проверки подтверждают:

- При 99 существующих точках восемь одновременных запросов дают один `201`, семь `409 monitor_limit` и ровно 100 записей в БД. Другой пользователь может создать свою точку.
- POST ограничен 10, GET — 60 запросами на пользователя в минуту; методы и аккаунты имеют независимые счётчики. Новый токен и другой IP не обходят лимит. Неверные JWT не расходуют счётчик аккаунта; через минуту запросы разрешаются снова. Ответ `429` содержит `Retry-After`.
- 45 записей с одинаковой датой читаются страницами 20 + 20 + 5 в устойчивом порядке. Добавление новой точки между страницами не создаёт повторов и пропусков прежних записей. Чужой курсор не раскрывает данные другого владельца. Неверные/слишком длинные курсоры, повтор и неизвестные параметры отклоняются.
- Существующие проверки авторизации, профиля, загрузок, CORS, методов и миграций также проходят.

Из `frontend/` на Node.js 24.6.0 прошли `npm run lint`, `npm test` (три регрессионных теста) и `npm run build` с TypeScript. Тесты исполняют реальный `session.ts` с управляемыми ответами транспорта. На исходной версии `session.ts` из родительского коммита все три теста падают, на исправленной проходят. `git diff --check` прошёл.

## Проверка Chrome с реальными API и PostgreSQL

Использованы production-сборка Next.js на `localhost:3100`, отдельный временный API на `localhost:18081` и тестовая PostgreSQL проекта `uptime-auth-tests`. Данные приложения не использовались. Playwright и сценарии находятся в `/tmp`; новые зависимости проекта не добавлены. Для тестов гонок ответы реального API задерживались в браузере; для проверки повтора страницы однократно подставлялся `503`.

Подтверждены:

- Пустой список, отмена и фокус, создание с интервалами 7, 600 и 7200 секунд, валидация URL/интервала, ошибки создания и списка с повтором, защита от двойной отправки, перезагрузка, изоляция аккаунтов.
- Реальный список из 45 точек: 20 + 20 + 5, без повторов. При `503` следующей страницы первые 20 сохраняются; повтор успешно догружает страницу.
- Вход другим аккаунтом во второй вкладке обновляет профиль и список первой вкладки. Задержанные ответы GET и POST прежнего аккаунта не добавляют его точки в новое состояние. Создание в новом аккаунте и последующая перезагрузка показывают только его точку.
- После перезапуска только API пять ранее созданных точек сохраняются и доступны при повторном входе.
- Аккаунт со 100 точками после перезапуска получает реальный `409 monitor_limit`; форма показывает понятную ошибку, сохраняет URL и не меняет список. Число записей в БД остаётся 100.
- На экране 360 px нет горизонтального переполнения. Необработанных ошибок JavaScript нет; localStorage/sessionStorage не содержат токенов.

Ограничение частоты хранится в памяти одного API-процесса и сбрасывается при его перезапуске. Квота защищена транзакцией PostgreSQL и сохраняется между перезапусками и экземплярами API. Ответ списка теперь содержит `next_cursor`; клиент должен запрашивать последующие страницы явно.
